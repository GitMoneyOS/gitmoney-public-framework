# A plain-language guide to GitHub for AI-assisted business work

**Hitsuyo Aku | GitMoney OS**

GitHub can help a founder-led business keep decisions, source material, drafts, code, and reviews inspectable. It is one operating surface, not a security guarantee or a substitute for management judgment. This guide explains a practical workflow without requiring the reader to become a software engineer.

## A few useful terms

| Term | Plain meaning | What it can and cannot do |
|---|---|---|
| Repository | A versioned work area | Stores selected files and history; access still depends on its actual settings. |
| Folder | A way to organize context | Helps people and agents find relevant material; it does not enforce read/write permission. |
| Skill or instruction file | Reusable task guidance | Can tell an agent what to check; it does not prove the check ran or passed. |
| Branch | A separate line of work | Keeps a proposed change apart from the target branch; production and data access require separate controls. |
| Commit | A recorded version | Shows what was committed; it does not by itself prove why a claim is true or who approved external use. |
| Pull request | A review surface | Lets reviewers inspect a proposed difference; review rules and actual approvals must be configured and followed. |
| Automated check | A programmed gate | Can test a defined condition; its value is limited to the behavior it actually checks. |

## A bounded workflow

1. **State the problem and source.** Name the decision or handoff that currently depends on memory. Link the records that show it and mark what remains unknown.
2. **Name the owner.** Decide who may authorize the work, who may edit the relevant system, and who independently reviews the result where the risk warrants it.
3. **Define the stage.** Give the person or agent only the context needed for discovery, architecture, build, or review. Specify the expected output and handoff.
4. **Enforce access separately.** Configure repository roles, tool grants, sandboxing, branch rules, secrets, and application permissions for the actual risk. Do not rely on folder names or prompts as a security boundary.
5. **Review the change.** Compare the diff with the source, scope, client permissions, and appropriate checks. Record the approval for the exact version and destination.
6. **Check the result.** A merged file is a repository event. A working route, safe permission boundary, collected payment, or client outcome needs its own evidence.
